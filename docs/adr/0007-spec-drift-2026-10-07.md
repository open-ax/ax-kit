## Decision

Answers to the three drift questions:

1. **IDL surface we implement — no.** `index.bs` is byte-identical across the
   range. No name, arity, type, or algorithm moved.
2. **Pinned draft date — no.** The header still reads 2 October 2026, which is
   what `SPEC_VERSION` records. `SPEC_VERSION.commit` stays `d61d0e6`.
3. **Conformance baseline — no.** No normative text changed, so the
   expected-failure lists are unchanged.

`6268aed6…` stands as the recorded baseline. No further change to
`.github/spec-drift.sha256` is required.

### Why the pin does not move to `6891d0e`

It would be defensible either way, so the reason is written down.

`SPEC_VERSION.commit` is the revision whose **text** this implementation
implements, not the newest revision. `6891d0e` changes no text. Moving the pin
would imply we implement a document we did not read, and — more practically —
it would put the pin out of step with `WPT_SHA`, which moves by finding the WPT
commit naming the *same change*. There is no WPT commit matching an
explainer-only commit in the proposal repository, so moving the pin would break
the correspondence that makes a suite run at that revision a test of the draft
we claim. The pin moves when text moves, and for no other reason.

This is the same rule that kept `57d396f` from being pinned ahead of
`433a194` in the 2026-09-29 triage recorded in
[`0003-spec-drift-2026-09-29.md`](./0003-spec-drift-2026-09-29.md).

### The upstream change that did affect normative text

Stated plainly because the next triage should not have to re-derive it:

**Upstream PR #330, "Remove origin-keyed agent cluster requirement", merged
2026-09-30T16:26:42Z by `domfarolino`, authored by `beaufortfrancois`, one
commit, `+0 / -18`, one file (`index.bs`).** It deleted the *is origin-keyed*
`SecurityError` step from the algorithms of `registerTool`, `getTools` and
`executeTool`, and closed issue #318.

That is what issue #10 was actually about. It removed normative text this
implementation depended on, and it is the change `351bf41` exists to answer.
The two later hash changes were an explainer arriving on top of it and carried
no normative weight.

`SecurityError` survives in the draft for the `exposedTo` potentially-trustworthy
check, which is unrelated and unchanged.

## Consequences

- Issue #10 can be closed. The baseline is recorded, the code follows the
  draft it names, and the reason is here.
- The next drift run compares against `6268aed6…` and opens no issue until the
  document changes again.
- If the next change is another explainer, this record's reasoning applies
  directly: read `index.bs` at both revisions, and if it is byte-identical,
  answer no to all three questions. That is a five-minute check, which is the
  point of writing it down.

## Revisit when

- The proposal's Bikeshed pipeline starts folding `index.bs` content out of the
  published document, or starts including linked explainers in the output. Then
  a hash change would no longer be safely triaged by comparing `index.bs`, and
  the triage procedure needs a different instrument.
- `6891d0e` is itself followed by a normative change before anyone notices.
  Then the triage question is not "is the pin still right" but "were we right
  to leave it" — and this record is the one to argue with.

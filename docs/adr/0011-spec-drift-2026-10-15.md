## Decision

Answers to the three drift questions:

1. **IDL surface we implement — no.** Verified by extraction and comparison,
   not by reading. No name, arity or type changed.
2. **Pinned draft date — yes.** The header moved 9 October 2026 to 15 October
   2026, so `SPEC_VERSION`, every README pin, the conformance baseline pin and
   the drift baseline move together in one change.
3. **Conformance baseline — yes, and the reason is a defect in this
   implementation.** All three commits change normative algorithms this code
   implements, and every divergence found was real. The claim is corrected by
   fixing them rather than by recording them.

### The three algorithm changes, and what each requires of us

**#345 — `unregister a tool` on an inactive document.** The draft now returns
without notifying when `targetDocument` is not fully active, because the
notification algorithm finds documents by walking the node navigable and an
unloaded document has none. `unregisterRecord` notified unconditionally.

**#337 — `executeTool` on a detached target.** The draft rejects with
`InvalidStateError` when the target document has no node navigable, before it
re-checks the target's eligibility. Our `executeTool` collapsed every failing
target into `NotFoundError`, so a detached target was reported as a missing
tool — a different fact, and one an agent could act on wrongly.

**#337/#347 — re-checking after `inputSchema` serialization.** `registerTool`
serializes `tool`'s `inputSchema` before writing the tool definition.
Serialization can run script through a `toJSON()` method, and that script can
do two things the pre-serialization checks have already passed:

- make the owning document no longer fully active (remove its `<iframe>`), and
- register a second tool under the same name.

The draft therefore re-checks both after serializing, rejecting with
`InvalidStateError`. Across the whole range `InvalidStateError` occurrences in
`index.bs` go 7 → 10: two here, one in `executeTool` above.

### Why these are reachable here at all, and the honest part

`registerTool` calls `checkSchemaNode` over the schema **before**
`JSON.stringify`, and that walk rejects an *enumerable* function value with
`TypeError("non-JSON value")`.

An earlier draft of this decision concluded from that the #347 re-checks were
unreachable and declined to implement them. **That was wrong, and the
correction matters more than the original claim.**

`checkSchemaNode` walks `Object.keys`, which is enumerable own properties only.
A **non-enumerable** `toJSON` is invisible to it — and `JSON.stringify` calls
`toJSON` regardless of enumerability. So:

```js
const schema = { type: "object" };
Object.defineProperty(schema, "toJSON", { value: () => { /* script */ return { type: "object" }; }, enumerable: false });
```

passes the schema walk and still runs script during serialization. Both #347
re-checks are therefore reachable, and both were violated. Measured on this
tree before the fix:

- A `toJSON` that registers the tool under the same name left **one** record
  standing, owned by the late registration. The squatter's registration was
  silently discarded. The draft requires `InvalidStateError`.
- A `toJSON` that removes the registering `<iframe>` left the registration
  **resolving successfully** on a document that was no longer fully active.
  The draft requires `InvalidStateError`.

The silent overwrite is the worse of the two: nothing reports it, and the tool
that survives is the one whose caller ran last.

So both re-checks are implemented. They cost two calls to functions already in
scope — `isFullyActive` and a `Map.has` — and the size budget absorbed them.

### Where they are placed, and why that is the load-bearing part

**Placing them immediately after `inputSchema` serialization was not enough,
and the first version of this decision got that wrong too.** `registerTool`
reads more caller-supplied properties after the schema: `input.title`,
`input.execute`, `input.annotations`, `options.signal`, `options.exposedTo`.
Every one is a getter or a method the caller controls, and each can run page
script. A check placed after serialization is therefore still satisfiable by
script that runs later.

Measured on this tree with the re-check after serialization:

- A `title` getter that registers the same name left the registration
  **resolving**, with the squatter silently overwritten. Identical to the
  `toJSON` case above, reached through a different read.
- An `execute` getter that removes the registering `<iframe>` left the
  registration **resolving** on a document whose `defaultView` is `null`.

The re-checks therefore sit **immediately before `state.tools.set`**, which is
the first statement after the last script-running read. Nothing the caller
supplies runs between the check and the write it guards. The placement costs no
bytes: it is a move, not an addition.

The `title` and `execute` getters are now asserted as tests alongside the
`toJSON` cases, because a regression here is invisible unless a test drives
that specific read.

The enumerable-function refusal remains a separate divergence, still carried as
`schema-serialisation-rejects-what-the-draft-allows`. Closing it means widening
the input-schema subset, which is ours by decision
([`0002-input-schema-subset.md`](./0002-input-schema-subset.md)). That is a
different change and is not taken here.

### What was fixed

**#345, in `unregisterRecord`.** The guard is stated where the draft states it,
immediately after the unconditional removal and before the notification.

There was a test asserting that no `toolchange` fires when the document has
gone inactive. **It was removed, because it could not fail** — deleting the
guard leaves it green. `collectVisibleDocs` already skips a document whose
`defaultView` is `null`, which is the same condition the guard tests, so an
unloaded document is never reached by the walk either way. The behaviour was
correct by accident rather than by rule.

The guard stays anyway: it is a step in the pinned draft, it costs three bytes,
and it defends a real future. If the document walk is ever changed to reach an
unloaded document's surviving descendants, the guard is what stops a spurious
notification. **#345 is not observable at this layer in this environment, and
that is recorded here rather than covered by a test that measures nothing.**

**#337, in `executeTool`.** A target whose node navigable is gone now rejects
with `InvalidStateError`. Previously every failing target collapsed into
`NotFoundError`, so a detached target was reported as a missing tool — a
different fact, and one a caller could act on wrongly. The check sits before the
eligibility re-check that does the collapsing.

**#337/#347, in `registerTool`,** immediately before the tool map is written:

- Re-check that the owning document is still fully active; reject with
  `InvalidStateError`.
- Re-check that the tool map does not hold this name; reject with
  `InvalidStateError`.

The abort listener is attached **after** both re-checks. Attached before them, a
rejected registration leaves a closure holding the document and the name that
nothing can reach to detach — measured at one leaked listener per rejection
before the move.

And in `unregisterRecord`, per #345: return without notifying when the document
is no longer fully active. Removal stays unconditional — the draft removes the
tool definition before it consults the document's state.

Every one of these except #345 is asserted by a test that fails without it, and
the serialization tests use a deliberately **non-enumerable** `toJSON`, because
an enumerable one is refused by the validator and would make the test pass
without exercising the re-check. #345 is the exception, and the reason is above.

### Why the suite pin does not move

`WPT_SHA` stays at `fe52996d4465f23617bce91927bdd58e6ce8f541`. The lag
recorded in ADR 0008 is unchanged and is joined by a second, larger one.

WPT `webmcp` has moved to `3a3a022` and carries six commits past our pin. Two
of them make moving the pin actively unsafe:

- `3a3a022` **reverts** *"WebMCP: Re-check for a duplicate tool name after
  serializing inputSchema"* (`91d7226`), blaming it for a Chromium build
  failure found by LUCI bisection. So the suite no longer tests the behaviour
  #347 added to the draft. The draft and its own suite now disagree, in the
  opposite direction to the lag ADR 0008 recorded.
- `15e7837` *"[3/N] WebMCP: Introduce the `Tool` interface object"* and
  `626f5bf` *"[2/N]: WebMCP: Identify tools by a unique ID for unregistration"*
  add suite files for a `Tool` interface and a declarative name-collision API.
  **Neither appears in the 15 October draft** — verified by listing every IDL
  declaration in both revisions above. They are staged work whose
  specification has not landed.

Moving the pin would import tests for an API that does not exist in the draft
this implementation targets, turning a truthful conformance number into a
false one. The pin moves when a suite revision carries the same change as the
pin it would be paired with.

## Consequences

- `SPEC_VERSION` moves to `15 October 2026` / `3279798`.
- `.github/spec-drift.sha256` records the live hash re-measured on 2026-10-15,
  which is **not** the value in issue #33. Recording the issue's value would
  leave the next scheduled run reporting a change that is not one.
- **The conformance expected-failure list: nothing gained, nothing lost.** That
  is Q3's second half answered, and it is measured rather than assumed. The
  scorer treats a stale entry as a failure as well as an unexpected one — a
  listed failure that now passes fails the run — so a green run is positive
  evidence that no entry became stale. Measured on 2026-10-15 against
  Chromium 153.0.8010.12, Firefox 155.0 and WebKit 26.6: 48 units run, 24 not
  run, 72 enumerated, 19 files passing, 29 failing or incomplete, 83 failing
  subtests, **zero unexpected and zero now-passing on all three engines**.

  The count is unchanged from the 9 October run because the pinned suite carries
  none of the three commits — see the next section. A re-derived list that
  matched the old one is the correct outcome when the suite cannot see the
  change, and recording it as unchanged is more useful than re-printing it.
- Issue #33 can be closed. All three questions are answered, and every code
  divergence found — #345, and both halves of #337/#347 — is fixed rather than
  recorded as a known gap.
- ADR 0008's `upstream-gap` entries stay. The gap widened; it did not close.

## Revisit when

- WPT carries #345 and #347, and the `Tool` interface lands in the draft. Then
  the pin moves and the re-checks gain upstream test coverage.
- The input-schema validator is revisited and admits an enumerable function
  value. Then the `schema-serialisation-rejects-what-the-draft-allows` gap
  closes, and the re-checks lose one of their two paths to reach script.
- The `Tool` interface is proposed. That is an upstream discussion first, and
  a rename or addition here only after it.
